# GitLab CI/CD

## Q: Explain your GitLab CI/CD architecture.

We use two long-lived branches: Develop and main. Developers create feature branches from Develop and open merge requests back to Develop. The MR pipeline has Security, Deploy, Test and Review stages. It creates a scratch org from the nightly snapshot, deploys metadata and dependencies in reference order, runs Apex tests and provides QA access to the scratch org. The MR title can contain skip-snapshot to use a regular scratch org; the pipeline also falls back to regular scratch-org creation if the nightly snapshot is unavailable. Failures trigger Google Chat notifications. Once merged to Develop, the QA pipeline builds and deploys the changed packages sequentially. For the biweekly release, we cut a release branch from Develop, raise an MR to main and manually run staging with package_list=all. It reuses the latest coverage-enabled package version or creates one, then builds/deploys packages with dependency-aware parallelism. Package IDs are published in GitLab Wiki, Google Chat sends status notifications and sfdx-project.json is updated. The production pipeline is manually run with the approved package names and IDs, followed by post-deployment validation and business-owner communication.

## Q: What are GitLab stages and jobs?

A stage is a logical phase in a pipeline, such as validation, testing or deployment. A job is an individual unit of work within a stage, such as creating a scratch org, deploying metadata or running Apex tests. Jobs in the same stage can run in parallel when dependencies allow, while stages normally run in sequence.

## Q: What is the purpose of before_script?

before_script contains commands that run before the main script of a GitLab job. I use it for common setup such as installing or checking CLI tools, preparing environment variables, setting the working directory and performing authentication setup. Sensitive values should come from protected or masked variables and must never be printed.

## Q: How do you trigger pipelines on merge requests?

I configure GitLab CI rules or workflow conditions to run when a merge request is opened or updated. The merge-request pipeline validates the proposed changes before they are merged. I also use branch and target-branch conditions so the right checks run for feature, integration and release branches.

## Q: How do you distinguish validation and deployment pipelines?

A validation pipeline checks whether a change can be safely integrated without making the final deployment to a shared target. It can create a scratch org, deploy the changed metadata and run tests. A deployment pipeline runs after the approved merge or release event and promotes the validated change to the intended environment.

## Q: How do you create Salesforce scratch orgs from GitLab?

For merge-request validation, our pipeline normally creates a scratch org using a snapshot generated by the nightly process. That gives QA and developers a consistent baseline for validating the proposed changes. We also support an explicit skip-snapshot condition: if the MR title contains skip-snapshot, the pipeline uses regular scratch-org creation. If the nightly snapshot failed or is unavailable, the pipeline falls back to a regular scratch org rather than stopping validation. Once the org is ready, the pipeline deploys metadata and dependencies in reference order and runs Apex tests. QA can access the scratch org to review the change, and failures are reported through Google Chat.

## Q: What is the difference between snapshot-based and regular scratch orgs?

A snapshot-backed scratch org starts from a prepared baseline created by the nightly snapshot process. It helps make MR validation more consistent and avoids repeating the full baseline setup for every merge request. A regular scratch org is created from the scratch-org definition and configured through the pipeline. In our implementation, the MR title can include skip-snapshot to select the regular path. We also use regular scratch-org creation as a fallback when the nightly snapshot is not available, so the validation process can continue.

## Q: How do you handle scratch org creation failures?

Our normal MR path provisions a scratch org from a nightly snapshot. If the MR title contains skip-snapshot, we deliberately use regular scratch-org creation. If the nightly snapshot failed or is unavailable, the pipeline also falls back to a regular scratch org. When investigating a failure, I check the Dev Hub authentication, snapshot availability, scratch-org definition, org allocation limits and Salesforce CLI output. Once the org is provisioned, the pipeline deploys metadata in reference order and runs Apex tests. The pipeline failure is sent to Google Chat so the team can respond. Credentials are kept out of logs.

## Q: How do you deploy metadata in dependency order?

We do not deploy changed components in arbitrary file order. The MR pipeline deploys metadata and dependencies in reference order into the scratch org. The scripts use the changed file list and a defined sequence to ensure prerequisites are available before components that reference them. At package level, the dependency graph across the nine unlocked packages determines the build and install order. Independent package jobs can run in parallel during staging, while dependent packages are sequenced. This balances speed with dependency correctness.

## Q: How do you execute Apex tests in CI/CD?

After metadata deployment, I use Salesforce CLI to run the required Apex tests and wait for completion. I capture the test run ID, results, failures and coverage information, then make the pipeline fail when required tests do not pass. Test selection depends on the validation scope and the organization's release policy.

## Q: How do you generate package.xml dynamically?

Our scripts use the Git source difference to identify which Salesforce metadata files changed. CI_COMMIT_SHA identifies the commit being processed, while CI_COMMIT_REF_NAME or CI_COMMIT_BRANCH identifies the triggering ref. The changed file list is passed between jobs as file_list. The automation calculates the delta, maps changed paths to metadata types and members, and generates the deployment manifest. A separate sequence or sequence_list controls processing order so prerequisites are handled before dependent components. Deletions are handled separately through destructive-change processing when required.

## Q: How do you identify changed metadata between Git branches?

I use Git diff between the merge-request target and source references, or between the release baseline and the current commit. The script filters Salesforce metadata paths and classifies additions, modifications and deletions. The result drives delta manifests, destructive changes and targeted validation.

## Q: How do you handle destructive changes?

I treat deletions as a separate, explicitly reviewed part of the release. The pipeline identifies deleted metadata and generates the appropriate destructiveChanges manifest for the target API version. I validate the deletion impact, obtain approval and deploy destructive changes in the correct order, often after dependent metadata has been updated.

## Q: How do you manage multiple Salesforce packages?

Our Salesforce DX monorepo contains nine 2GP unlocked packages across four orgs. We manage package boundaries, versioning, dependencies and ancestor tracking through the project configuration and package-version process. The pipeline detects changed packages and uses dependency information to determine the build and installation order. In the QA flow, changed packages are built and deployed sequentially. During staging, package_list=all requests the full package set. The workflow reuses the latest coverage-enabled package version when available, otherwise creates a new version. Independent package jobs can run in parallel, while dependent packages follow the required sequence. We record generated package IDs in GitLab Wiki and update sfdx-project.json so the selected versions are traceable.

## Q: How do you manage secrets and credentials in GitLab?

We use protected GitLab variables together with Google Cloud Secret Manager for sensitive deployment credentials. Salesforce authentication is performed through JWT-based authentication and Salesforce CLI. The pipeline reads the required secret at runtime and uses it for the target org login without echoing it or storing it in artifacts. One project variable is SF_SFDX_URL_DEV, which contains the SFDX auth URL for the Dev sandbox. CI_COMMIT_SHA identifies the source revision, while CI_COMMIT_REF_NAME and CI_COMMIT_BRANCH provide branch context. Protected values are restricted to the appropriate protected branches and pipeline contexts.

## Q: How do you implement security checks in CI/CD?

I add automated checks early in the pipeline so issues are identified before merge or deployment. Depending on the project, this includes secret detection, static code analysis, dependency review and policy checks. I also protect branches and production environments, restrict credentials and retain audit evidence.

## Q: How do you troubleshoot a failed GitLab job?

I first identify which stage failed: Security, scratch-org provisioning, metadata deployment, Apex testing, package creation or package installation. I inspect the job log and commit/ref context, then verify authentication, protected-variable access, snapshot availability, metadata dependencies and package-version prerequisites. If the failure is snapshot-related, the workflow can fall back to a regular scratch org. If it is a metadata or package-order problem, I correct the source or dependency sequence and rerun validation. Pipeline failures are also reported to Google Chat, giving the team a clear notification and a starting point for investigation.

## Q: How is Apex PMD integrated into your Salesforce CI/CD process?

Apex PMD is used as a static analysis check to identify code-quality and potential defect patterns in Apex before changes move further through the pipeline. The pipeline runs the configured PMD analysis against the source, captures the findings and makes the results available for review. PMD complements Apex unit tests: it detects rule-based code issues, while tests validate behavior. I would confirm the exact job stage and failure threshold from the current pipeline YAML and ruleset before describing a specific blocking policy.

## Q: Where are PMD findings and Apex coverage results tracked?

The PMD scan output is reviewed as part of code quality checks, and scheduled Apex and package coverage results are published to the GitLab Wiki for team visibility. The GitLab Wiki provides a place to review the latest scheduled results, while the source repository and pipeline configuration preserve the rules and execution process. I distinguish the latest report from a historical result and verify its timestamp before quoting counts or coverage percentages.

## Q: How do you decide whether a PMD finding should block a merge?

I use the team's agreed severity and quality policy rather than treating every finding identically. High-risk findings can be configured to fail the pipeline, while lower-priority findings can be reported for review and remediation. I consider whether the finding is new or pre-existing, the affected code path and the risk of the change. The exact blocking threshold must match the PMD ruleset and pipeline configuration; I do not quote a severity threshold unless I have verified it.
